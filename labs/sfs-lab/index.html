    SFS Lab · A Multithreaded File System¶

    File systems & concurrency · Keywords: disk blocks, file lifetime, fine-grained locking · sfs-disk.c

    AI-assisted solution

    This implementation and writeup were completed with AI assistance because time was limited and the lab had low marginal value for my later parallel-computing direction. It is recorded explicitly as an AI-assisted solution, not presented as independent work.

    Verified locally

    make baseline && ./test-sfs -q → 22 / 22 automatic points: correctness 12/12, ThreadSanitizer clean across three fuzzed schedules, and performance 10/10 at 3.40× the calibrated global-mutex baseline.

    SFS — the Shark File System — is a small but real on-disk file system: files, a directory, and free-space management, all persisted to a disk image. You implement it in a single file, sfs-disk.c, against a fixed API. What makes it more than a data-structure exercise is the second half: the file system has to be thread-safe and scalable, not merely correct.

    The assignment

    Implement sfs-disk.c against the interface in sfs-api.h, in two parts:

    • Correctness — finish the three operations left unimplemented in the handout: sfs_getpos, sfs_seek, and sfs_rename. rename has to be atomic: if the new name already exists, it is replaced with no window in which a concurrent thread sees it missing.
    • Concurrency — add locking so the file system is thread-safe and actually scales, so that operations on independent files proceed in parallel. Grading compares you against a one-global-mutex baseline: coarse locking passes correctness but forfeits the performance score.

    The disk image¶

    An SFS disk is just a byte array — an mmap'd file — divided into fixed 512-byte blocks. Block 0 is the super block; every block is found by number, so block N lives at byte offset 512 * N.

       an SFS disk = an mmap'd file, split into 512-byte blocks
   +---------+---------+---------+---------+- - -+
   |  block  |  block  |  block  |  block  |     |
   |    0    |    1    |    2    |    3    | ... |
   | (super) |         |         |         |     |
   +---------+---------+---------+---------+- - -+
   block N starts at byte offset  512 * N

    Every block except the super block opens with a 12-byte header — a 4-byte type tag (FREE / FILE / DIR) plus 4-byte prev and next block numbers. A FILE block uses all 500 remaining bytes for data; a DIR block uses 20 bytes of padding followed by fifteen 32-byte directory entries. Those prev/next fields are the whole trick: blocks are threaded into linked lists.

       FILE block (512 B)
   +--------------------------------+
   | type[4] | prev[4] | next[4]    |
   +--------------------------------+
   | 500 B file data                |
   +--------------------------------+

   DIR block (512 B)
   +--------------------------------+
   | type[4] | prev[4] | next[4]    |
   +--------------------------------+
   | 20 B unused / padding          |
   +--------------------------------+
   | 15 x 32 B directory entries    |
   +--------------------------------+

   super block (block 0, 512 B)
   +--------------------------------+
   | magic[8] + n_blocks[4]         |
   | freelist[4] + next_rootdir[4]  |
   +--------------------------------+
   | 12 B unused / padding          |
   +--------------------------------+
   | 15 x 32 B root-dir entries     |
   +--------------------------------+

   type[4] = FREE | FILE | DIR

    So the entire file system is a handful of linked lists of blocks:

       a file = a chain of FILE blocks, linked by each header's prev/next:

     dir_entry.first_block
              |
              v
            [FILE] <-> [FILE] <-> [FILE] ---> 0     (0 = end)

   root directory = 15 entries in the super block, then a chain of
                    DIR blocks containing 32-byte entries
                    { first_block, size, name[24] }
   free space     = unused blocks threaded onto a free list

    A block number of 0 in any field means "none" — the on-disk equivalent of a null pointer (block 0 is the super block, so it is never a valid link target).

    The operations¶

    The API is a small POSIX-flavored set. Positions are per-descriptor; the file system is a single flat directory.

    Group Operations Notes
    Image sfs_format, sfs_mount, sfs_unmount create / attach / detach a disk image
    Files sfs_open, sfs_close open-or-create; returns an SFS "descriptor"
    I/O sfs_read, sfs_write short counts allowed; write grows the file
    Position sfs_getpos, sfs_seek positions are independent per descriptor; seek clamps to [0, size]
    Namespace sfs_remove, sfs_rename Unix-style unlink; overwrite-rename is atomic
    Listing sfs_list one name per call via an opaque cookie
    Size extensions sfs_fstat, sfs_ftruncate unscored developer-edition operations

    Two carry non-obvious contracts. rename must atomically replace an existing target. And sfs_list hands back one filename per call through a cookie, while concurrent namespace changes must never expose a torn entry.

    One file, three layers¶

    An open file is not represented by one object. SFS separates the name stored on disk, the state shared by every opener, and the position private to one descriptor:

    openFileDescTable[fd]
        |
        v
  sfs_mem_filedesc_t          one per open descriptor
  +------------------+
  | currPos          |        independent seek position
  | fileEntry -------+---+
  +------------------+   |
                         v
                   sfs_mem_file_t       one per open file
                   +----------------+
                   | refCount       |
                   | unlinked       |
                   | pthread lock   |  serializes this file's data
                   | diskFile ------+---+
                   +----------------+   |
                                        v
                                  sfs_dir_entry_t      persisted in the image
                                  { name, size, first_block }

    Opening the same name twice therefore creates two descriptor objects with separate currPos values, but both point to one sfs_mem_file_t. The shared object owns the per-file mutex and points at the one directory entry containing the size and first block:

    typedef struct sfs_mem_file_t {
    uint32_t refCount;
    int unlinked;
    pthread_mutex_t lock;
    sfs_dir_entry_t *diskFile;
    sfs_dir_entry_t unlinkedFile;
} sfs_mem_file_t;

typedef struct sfs_mem_filedesc_t {
    sfs_mem_file_t *fileEntry;
    size_t currPos;
} sfs_mem_filedesc_t;

    sfs_open takes the directory and open-table write locks, finds or creates the on-disk entry, reuses an existing memory-file object when one exists, and allocates a free descriptor slot. This is why a file lock protects file contents while a descriptor-slot lock protects only one caller's position and pointer.

    Unlink changes reachability, not open-file lifetime¶

    Removing a closed file can return its blocks immediately. Removing an open file cannot: its descriptors must continue to work even though the name has disappeared. unlinkDirectoryEntry copies the directory entry into the memory-file object, redirects diskFile, and only then clears the visible slot:

    if (open != NULL) {
    pthread_mutex_lock(&open->lock);
    open->unlinkedFile = *entry;
    open->diskFile = &open->unlinkedFile;
    open->unlinked = 1;
    pthread_mutex_unlock(&open->lock);
} else if (entry->first_block != SFS_EMPTY_FILE_BLOCK) {
    freeBlocks(entry->first_block);
}
memset(entry, 0, sizeof *entry);

    The final sfs_close sees refCount reach zero and frees the saved block chain. This small indirection gives SFS the Unix rule: unlink removes a name now; it destroys the underlying file only after the last open reference is gone.

    Part 1 · Completing the API¶

    Positions belong to descriptors¶

    sfs_getpos validates the descriptor and returns its byte position. sfs_seek computes the new position without overflowing on SSIZE_MIN, then clamps it to the file's current size:

    if (delta < 0) {
    size_t distance = (size_t)(-(delta + 1)) + 1;
    position = distance > position ? 0 : position - distance;
} else {
    size_t distance = (size_t)delta;
    position = distance > file_size - position
                   ? file_size
                   : position + distance;
}

    The -(delta + 1) + 1 form matters because directly negating the most negative signed integer is undefined behavior.

    Rename holds the namespace as one transaction¶

    sfs_rename takes exclusive directory and open-table locks for the entire operation. If the target exists, it is unlinked first while both locks remain held; then the source entry's name is replaced:

    pthread_rwlock_wrlock(&directoryLock);
pthread_rwlock_wrlock(&openTableLock);

sfs_dir_entry_t *old_entry = findDirectoryEntry(old_name, NULL, NULL);
/* validate old_entry and handle old_name == new_name */

sfs_dir_entry_t *new_entry = findDirectoryEntry(new_name, NULL, NULL);
if (new_entry != NULL)
    unlinkDirectoryEntry(new_entry);

size_t len = strlen(new_name);
memcpy(old_entry->name, new_name, len);
memset(old_entry->name + len, '\0', SFS_FILE_NAME_SIZE_LIMIT - len);

pthread_rwlock_unlock(&openTableLock);
pthread_rwlock_unlock(&directoryLock);

    Other threads therefore observe either the old namespace or the completed new namespace, never the half-finished state between target removal and source renaming.

    An overwritten target may still be open. The same unlink path above preserves its private directory-entry copy, so existing descriptors keep working and the blocks return to the free list only after the final close.

    Reads and writes walk 500-byte payloads¶

    Each 512-byte file block spends 12 bytes on its header, leaving BLOCK_DATA_SIZE == 500 bytes. A read first caps its byte count at EOF, finds the block containing currPos, then copies one block-bounded chunk at a time:

    size_t totalToRead = sizeMin(fileSize - currPos, len);
sfs_block_file_t *diskBlock =
    accessFileBlock(blockForPosition(first, currPos));
size_t blockPos = currPos % BLOCK_DATA_SIZE;
size_t chunkSize =
    sizeMin(roundUp(currPos, BLOCK_DATA_SIZE) - currPos, toRead);

for (;;) {
    if (chunkSize > 0) {
        memcpy(buf, &diskBlock->data[blockPos], chunkSize);
        buf += chunkSize;
        toRead -= chunkSize;
    }
    if (toRead == 0)
        break;
    blockPos = 0;
    chunkSize = sizeMin(BLOCK_DATA_SIZE, toRead);
    diskBlock = accessFileBlock(diskBlock->h.next_block);
}

    At an exact block boundary the first chunkSize is zero; the loop advances once before copying. Otherwise the first chunk consumes the remainder of the current block, and later chunks start at offset zero. In either case a chunk never crosses a block. Only after all copies finish does the descriptor advance by totalToRead.

    Writes use the same walk in the other direction. Before touching the file, sfs_write calculates the final position and allocates all additional blocks it will need:

    if (endPos > fileAllocSize) {
    size_t newSize = roundUp(endPos, BLOCK_DATA_SIZE);
    uint32_t extra = (newSize - fileAllocSize) / BLOCK_DATA_SIZE;
    firstNewId = allocateBlocks(extra, SFS_BLOCK_TYPE_FILE);
    if (firstNewId == 0) {
        pthread_mutex_unlock(&file->lock);
        pthread_mutex_unlock(&descriptorLocks[fd]);
        return -ENOSPC;
    }
}

    The new chain is attached only when the copy reaches the old tail. Allocation failure therefore leaves the original file unchanged instead of exposing a partial write. An empty file uses the sentinel SFS_EMPTY_FILE_BLOCK; its first successful write swaps that sentinel for the new chain's head.

    Part 2 · Locking, for correctness and scale¶

    The provided baseline wraps every call in one global mutex. That is correct, but unrelated files cannot make progress together. The final design gives each shared resource only the lock it needs:

       directory rwlock     names, directory slots, directory-block chain
   open-table rwlock    descriptor/file-table lifetime and cold table scans
   fd-slot mutex        one descriptor pointer and its current position
   per-file mutex       file size, block chain, and file contents
   allocator mutex      free-list allocation and reclamation

    The lock order is always:

    directory → open table → fd slot → file → allocator

    Functions skip locks they do not need, but never reverse that order. Namespace operations use the left side of the chain; ordinary I/O starts at its fd slot. Allocation is a short final critical section only when a file grows or releases blocks.

    Keep the global table off the hot path¶

    The first correct version held a shared open-table lock around every read, write, getpos, and seek. It passed all functional tests and TSan, but measured only 5.20 M calls/s, or 0.56× the one-mutex baseline. A reader lock is not free: all eight threads still modify the same rwlock cache line.

    The final version uses a permanent mutex for each fd slot. A data operation locks its own slot to pin the descriptor, then locks only that file:

    read / write / seek:  fd-slot lock → per-file lock
getpos:               fd-slot lock
write that grows:     fd-slot lock → per-file lock → allocator lock

    Different files now touch different fd and file locks. The open-table lock remains for open, close, namespace operations, and the unscored truncate path, but disappears from the millions of timed I/O calls.

    Derive the block from the position¶

    The starter caches startBlock and currBlock in every descriptor. Those cached pointers must all be repaired when an empty file gains its first block or when ftruncate releases blocks. Updating every live descriptor would require a global table scan on the write path.

    The solution keeps only currPos and derives the current block from the file's on-disk head while holding the file lock. SFS files are small linked chains, and the performance workload stays in one block, so this removes shared bookkeeping without creating a measured cost. It also prevents stale block IDs after truncation.

    Directory reads must join the file lock¶

    first_block lives inside a directory entry but changes when the first write allocates a block. Protecting only directory names was therefore insufficient: TSan caught sfs_list and sfs_open reading first_block while another thread wrote it. Directory scans now find the corresponding open-file record and briefly take its file lock before inspecting that field.

    This is the useful lesson from the lab: synchronization follows the data, not the function name. A directory lookup can still depend on mutable file metadata.
